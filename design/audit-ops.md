# 012 运营页审计（概览 / 工作台）

面向重设计前的证据整理。范围：`src/client/overview.tsx`、`dashboard.tsx`、`pipeline.tsx`、`pms.tsx`、`widgets.tsx`、`rows.tsx`、`controls.tsx`、`marks.ts`，以及它们读取的服务端形状 `src/app/views/overview.ts`、`src/app/views/pms.ts`、`src/app/cards.ts`。

判断依据是面板自己的设计原则（`docs/005-panel.md` 第 67–75 行）与真实使用场景（`docs/011-interaction-scenarios.md`）。原则里最常被违反的三条是：**5 号"诚实状态"**（一个数字等于它链过去的那个列表的长度）、**6 号"默认安静"**（健康状态不占额外空间，问题必须可执行）、**2 号"定义精确"**（分类互斥且可判定）。

本文只做诊断，不含方案稿。所有结论都带 `文件:行号`，行号对应审计时的仓库状态。

## 2. 问题清单

严重度按"对三个问题的伤害"判定：**高** = 直接让某个问题答错或让操作员做错事；**中** = 让扫描变慢、让状态不可信；**低** = 一致性、措辞、边缘场景。

### 2.1 信息架构

---

**F-01｜高｜流水线「执行中」站点的数字是工人数，链过去的却是工单列表**

- **位置**：`src/client/dashboard.tsx:65-66` — `{ id: 'running', count: data.executor.running, note: t('pmsFlowNote.running', { queued }), onOpen: open({ page: 'execution', query: { filter: 'working' } }) }`
- **发生什么**：站点上的大数字 `data.executor.running` 是**正在跑的工作 Session 数**（服务端 `src/app/views/pms.ts:235` 的 `running` 来自 `runtime.executor.activeCount()`，`src/app/http.ts:173`）。点下去打开的 Execution 页 `filter: 'working'`，它的列表定义是 `ticketStage(ticket).stage === 'working'`（`src/app/views/tickets.ts:38`）。处于 `working` 阶段但还在排队等槽位的工单算在这个列表里；正在跑的工单在两次轮次之间又会掉到 `idle` 阶段、不在这个列表里。**数字和它链过去的列表不是同一个量。**
- **为什么伤害**：违反原则 5（诚实状态），直接伤害问题二"系统健康吗"。操作员看到"2 个执行中"、点进去看到 3 行，无法判断是哪个环节错了，久而久之不再相信这张图。
- **建议**：把 `working` 阶段的工单数加进 `PmsPipeline`，站点数字用这个数，工人数改放到站点说明里。

---

**F-02｜高｜「完成」站点数的是过去 24 小时，打开的却是全部历史工单**

- **位置**：`src/client/dashboard.tsx:69-70`（`count: data.pipeline.ended` → `filter: 'ended'`）；服务端 `src/app/views/pms.ts:219` `ended = store.tickets.list().filter(ticket => ticket.ended && Date.parse(ticket.ended.at) >= Date.now() - day)`；列表侧 `src/app/views/tickets.ts:39` `stage === 'ended' ? store.tickets.list() : store.tickets.open()`
- **发生什么**：数字是"最近 24 小时结束的工单数"，列表是"历史上所有结束过的工单"，且分页 20 条。数字与列表长度可以差一个数量级。
- **为什么伤害**：违反原则 5。更麻烦的是，7 个站点里有 2 个是"过去 24 小时"口径（触发、完成），5 个是"此刻"口径，而这件事只写在 12px 的说明行里（F-19 还会把这行截断）——操作员无从判断这七个数字是不是同一个时间维度。
- **建议**：把"24 小时"从说明行提到站点名或角标上，并让「完成」站点的目标页也是同一个 24 小时窗口。

---

**F-03｜高｜工作台的「待处理」一个列表里混着四种状态，且不排序**

- **位置**：`src/client/pms.tsx:39` — `const tasks = filter === 'archived' ? data.archived : filter === 'declined' ? data.declined : data.tasks`；状态来源 `src/app/views/pms.ts:175-176`（`undecided | working | waiting | ended` 四种都进 `data.tasks`）；顺序来自 Redmine 的 `updated_on desc`（`src/app/views/pms.ts:142` `listIssues(..., sort: 'desc', limit: 100)`）
- **发生什么**：「待处理」这一列同时装着：没人判断过的（待分析）、Agent 正在干的（分析中）、**等着操作员的（等你处理）**、已经推完补丁的（已完成）。排序是"最近更新的在前"，所以真正需要人处理的那条可能排在第 40 位。
- **为什么伤害**：这是对问题一"现在有需要我的事吗"最直接的伤害。概览的流水线知道有多少条在"等人"（`pipeline.waiting`），工作台却不把它们排在前面。
- **建议**：按"等人 → 分析中 → 待分析 → 已完成"分组排序，组内保持 Redmine 的时间序。

---

**F-04｜高｜概览把问题二的答案放在问题一的前面**

- **位置**：`src/client/overview.tsx:66-79` — `LiveDashboard` 先渲染，「待处理工单」在 `:70` 之后
- **发生什么**：面板文档（`docs/005-panel.md:7-11`）把三个问题按优先级排成"现在有需要我的事吗"第一，但页面先给横幅、再给 7 站图（最高的一块，约 200px），把唯一回答问题一的列表推到折叠线以下。
- **为什么伤害**：操作员打开面板回答 Agent 的提问，要先滚过一块不解决他问题的图。原则 3 也说"Overview 先讲系统实时状态"，两条原则在这一点上互相拉扯——这正是重设计要拍板的地方，不是可以两边都留的。
- **建议**：把"等你处理 N 条"提到横幅里（现在只有 11px 的胶囊），并把工单列表放在图表之前。

---

**F-05｜中｜「评估」站点打开的是"决策记录"页，不是"正在评估"**

- **位置**：`src/client/dashboard.tsx:59-62` — 评估站 `count: data.pipeline.evaluating` → `{ page: 'eval' }`；Eval 页默认筛选 `work`（`app.tsx:154`），`work = 'accept,reopen'`（`client/api.ts:100-103`），列的是**决策**；而 `pipeline.evaluating` 数的是**正在评估中的线程**（`src/app/views/pms.ts:228`）
- **发生什么**：图上写"3 个正在评估"，点进去是一页过去的决策记录，长度和那个 3 毫无关系。
- **为什么伤害**：伤害问题二。操作员无法用图上的数字去核对页面上的任何一行。
- **建议**：给 Eval 页加一个"进行中"筛选（列正在评估的线程），站点指向它。

---

**F-06｜中｜概览接口算好了一份 24 小时流量摘要，页面一个字都没显示**

- **位置**：`src/app/views/overview.ts:71-78` 返回 `{ problems, person, executor, flow, policyVersion }`；`src/client/overview.tsx:63-78` 只读 `data.person` 和 `data.problems`
- **发生什么**：`flow`（24 小时内 收到 / 被过滤 / 触发 / 已判断 / 已接受 / 正在评估 / 被丢弃）、`executor`（running / maxWorkers / idle）、`policyVersion` 每次轮询都在服务端算好并传到客户端，然后被丢弃。
- **为什么伤害**：面板手上已经有回答"系统在做对的事吗"最有用的一组数字（进来 100 条、过滤掉多少、判了多少、接了多少），却一个都没露出；同时这是一份持续传输的死负载，说明概览页是半成品。
- **建议**：在流水线图下方加一行 24 小时漏斗（到达 → 判断 → 接受 → 丢弃），并删掉页面不用的字段。

---

**F-07｜中｜列表超过 100 条时，Redmine 事务会被静默截断，"待处理"里可能根本没有待处理的任务**

- **位置**：`src/app/views/pms.ts:142` — `listIssues(commands, { assignedTo: 'me', status: closed ? '*' : 'open', sort: 'desc', limit: 100 })`；`:207` 才把已关闭的过滤掉 `else if (!inbox.closed.has(issue.status?.id ?? 0))`
- **发生什么**：为了"归档过的已关闭事务也要留在列表里"（`:141` 注释），请求会带上全部状态、按更新时间倒序取前 100 条。如果绑定账号名下最近有 100 条事务、其中 60 条已关闭未归档，那么**排在第 41 名以后的未关闭任务根本不会出现在工作台**，也没有任何"已截断"的提示。
- **为什么伤害**：伤害问题一。一件真的需要操作员处理的事，可能压根没进过列表。`pipeline.tasks` 也是这个截断后的长度，所以概览和工作台彼此一致，但一致的是一个不完整的集合。
- **建议**：请求只用未关闭状态，关闭的事务靠本地归档标记单独取；并在返回里带上"还有更多"标记。

### 2.2 层级与扫描

---

**F-08｜高｜同一个数字在概览上被打印三次，三种字号，三种形态**

- **位置**：
  - 「等人 N」：横幅胶囊 `dashboard.tsx:40`（11px Tag）→ 流水线站点 `dashboard.tsx:67-68`（22px 大数字）→ 「待处理工单」区块计数 `overview.tsx:70`（14px `.dt-count`）
  - 三者是同一批工单：`overview.ts:73` 的 `person` = `stage === 'person'`，`pms.ts:231` 的 `waiting` = 同样定义
  - 「执行中 N」：横幅大数字 `dashboard.tsx:31,43`（28px）→ 流水线站点 `dashboard.tsx:65`（22px）
  - 「排队 N」：横幅胶囊 `dashboard.tsx:39` → 站点说明行 `dashboard.tsx:65`
- **发生什么**：一个数字在屏幕上出现三次，而三次都是同一个事实。最需要被看见的那个（等人）反而是三次里最小的那个（11px 胶囊）；最显眼的 28px 大字（执行中）和图上 22px 的站点数字也是同一个数。
- **为什么伤害**：直接伤害问题一和问题二的扫描效率。眼睛无法判断"这个 2 是新的事实还是刚才那个 2"，也让 28px 的视觉预算浪费在重复信息上。原则 1 说"一个数字只有在它改变操作员行为时才出现"。
- **建议**：一个事实只印一次。等人数量只留横幅上的一处（并放大），工位占用搬回执行页，排队数只留在流水线站点的说明里。

---

**F-09｜中｜流水线里的条形图在比较互不可比的量**

- **位置**：`src/client/pipeline.tsx:26-29` `share()` 用全图最大计数做分母；`:39-40` 把结果写进条形填充宽度
- **发生什么**：7 个站点的计数分别是 Redmine 任务数、24 小时触发数、正在评估数、未结束工单数、运行中的工人数、等人的工单数、24 小时完成数（`dashboard.tsx:57-70`）。过去一天来了 120 条触发、手上有 3 个任务时，"触发"条占满 100%，其余全是 2–3% 的细线——图在传达一个并不存在的量级差。条形还标了 `aria-hidden`（`pipeline.tsx:39`），即纯装饰但带误导。
- **为什么伤害**：伤害问题二。操作员会读出一个不存在的规模结论。
- **建议**：去掉跨站点的共享比例条（每站已有数字），或改成"占各自分母的比例"并把分母写出来。

---

**F-10｜中｜系统问题全部用同一种"错误"颜色画出来，无法分级**

- **位置**：`src/client/overview.tsx:15-16` — 所有问题行共用 `dt-row dt-link dt-att dt-att-error`；`client.css:361-364` 把左边条和标题都画成 `--dsw-alias-state-error-primary`
- **发生什么**：问题种类跨度很大——部署检查没通过、来源没开、名单是空的、**处理已暂停**、运行时错误、评估超时、评估不可用、回复发送失败（`src/app/views/overview.ts:48-66`）。它们在屏幕上长得一模一样，包括"点一下就能恢复的已暂停"。
- **为什么伤害**：伤害问题二。操作员必须逐条读完才能挑出该管的那一条。
- **建议**：给每个 kind 定一个严重度（错误 / 警告 / 提示），列表按严重度排序，部署类问题保持最前。

---

**F-11｜中｜工作台行里的状态徽标是 11px，跟工单号一样大，而且五种状态只定义了三种颜色**

- **位置**：`src/client/pms.tsx:21-22` — `#id / 项目 / 状态 / 时间` 在 `.dt-task-meta`（`client.css:460`，11px），Agent 状态在 `.dt-task-state`（`client.css:462-466`，11px）
- **发生什么**：一行的视觉重心落在 13px 的标题和 11px 的元信息上，而这行真正要看的（待分析 / 分析中 / 等你处理 / 已完成）是一枚小灰牌，压在元信息下面。`client.css:462-466` 只为 `working`（蓝）、`waiting`（琥珀）、`declined`（灰）、`ended`（绿）定了色，**`undecided`（待分析）没有规则**，落回默认灰——而待分析恰恰是数量最多的状态。
- **为什么伤害**：伤害问题一。状态是这一行的意义所在，却是最小、最不显眼的那个元素。
- **建议**：把状态提到行首做 13px 的前导标签加一个点，五种状态全部定义颜色。

---

**F-12｜中｜流水线图例只解释了 4 种色调里的 3 种，而没解释的那一种是出现最多的**

- **位置**：`src/client/dashboard.tsx:81-85` 图例只有 进行中 / 等人 / 已完成；`pipeline.tsx:8` 的 `StationTone` 有 4 种（active / waiting / done / idle）；`client.css:64` 灰色是 idle 的默认色
- **发生什么**：「任务」「工单」两站被写死为 idle（`dashboard.tsx:57,63`），任何空站也是 idle——7 个站里常态有 4 个是灰点，图例里却没有灰色这一项。
- **为什么伤害**：伤害问题二。图例是这张图的钥匙，钥匙少了一格，操作员分不清"灰 = 没事"和"灰 = 这类工作不在这里统计"。
- **建议**：补一个"空闲"图例项，或让 idle 干脆不画点——让亮起来的点成为唯一的信号。

### 2.3 交互与状态反馈

---

**F-13｜高｜归档后这一行直接消失，没有任何提示，和"删除"长得一模一样**

- **位置**：`src/client/pms.tsx:15`（`toggle.run()`）→ `src/client/provider.tsx:42-56`（`useAction` 只做 reload + 失败 toast，成功不发提示）→ 服务端 `src/app/views/pms.ts:205` 把任务挪进 `archived`
- **发生什么**：点归档后，这一行从「待处理」里没了。没有 toast、没有撤销、没有提示说它去了哪。归档按钮是纯图标（`pms.tsx:28`，图标 `inbox` / `refresh`，`title` 属性才是"归档"），删除按钮在 24px 之外（`pms.tsx:29-30`），同样是幽灵图标按钮 + 确认弹窗。两者在视觉上是一对。
- **为什么伤害**：伤害问题一。操作员以为归档了（其实能撤销）还是删掉了（不能撤销），在下一次点击"删除"之前没有依据。原则 6 要求"等待人的行直接给出它的动作"，这里动作给了但反馈没了。
- **建议**：归档后弹一次 toast 并给一个"撤销"，同时把归档/删除做成形状可区分的两个控件（归档带文字或用不同图标语义）。

**F-14｜中｜九类系统问题里有两类完全没有动作**

### 2.5 文案与术语

---

**F-24｜中｜界面里「工单」指 Ticket，但场景文档 docs/011 里「工单」指 Redmine 事务**

- **位置**：界面侧 `locales.ts:135,138` — `pmsFlow.tasks` = 任务（Redmine 事务）、`pmsFlow.tickets` = 工单（Agent 的 Ticket）；`src/client/locales.ts:203` `pendingTickets` = 待处理工单（列的是 Ticket）。文档侧 `docs/011-interaction-scenarios.md:15-16` — "代理接到的每一个**工单**（指派给 `dev` 的）"，其 `:20-25` 的状态表正是界面的 `pmsState.*` 五态（待分析 / 未处理 / 分析中 / 等你处理 / 已完成）
- **发生什么**：同一个词在面板 UI 和面板自己的场景清单里指向两个不同的对象，而场景清单描述的正是这套 UI 的行为。
- **为什么伤害**：重设计时如果照着 docs/011 画，"工单"就会被画成 Redmine 事务，和现有实现整体对不上；这是文案问题，但已经造成过一次文档与实现的口径分裂。

---

**F-25｜中｜「2 / 4 个任务在跑」这句话里的单位是错的**

- **位置**：`src/client/dashboard.tsx:31,43-44` — 数字是 `{running} / {max}`，即**运行中的 worker 数 / worker 总数**；说明文字是 `t('pmsProjectsRunning')` = "个任务在跑 / tasks running"（`locales.ts:131`）
- **发生什么**：中文连读是"2 / 4 个任务在跑"，字面意思是"4 个任务里有 2 个在跑"，但分母 4 是**并发 worker 上限**，不是任务数。执行页有同样的写法（`execution.tsx:32-33`，"执行中 2 / 4"）。locale 键名还留着旧词 `pmsProjectsRunning`（"projects running"），说明这个字符串改过而键没改。
- **为什么伤害**：伤害问题二。操作员会把"4"理解成队列里的任务数，从而高估或低估系统的实际负载。
- **建议**：把数字和它的单位拆开写清——"2 / 4 个工位在跑"（或"2 个 worker 在跑，上限 4"），并让键名跟着改。

---

**F-26｜中｜「待处理工单」和「待处理」两个列表在中文里长得很像，内容却不是一批东西**

- **位置**：概览 `pendingTickets` = 待处理工单（`locales.ts:203`，列的是等着人的 Ticket）；工作台 `pmsFilterActive` = 待处理（`locales.ts` 的 `pmsFilterActive`，列的是 Redmine 事务）
- **发生什么**：概览上写"待处理工单 2"，工作台上写"待处理 12"，两处中文前缀相同但一个是 Agent 的 Ticket、一个是 Redmine 事务。
- **为什么伤害**：伤害问题一。操作员会把两个数字当成同一件事的两种说法，而它们分别来自两张不同的表。注意：「已完成」也在「待处理」里是设计决定（`docs/011-interaction-scenarios.md:24` 明确写了），要改的不是这个归类，而是**筛选器名字**与它内容的矛盾。
- **建议**：给工作台那个筛选换一个不与概览撞词的名称（"我的任务" / "未归档"），或给概览那个加上限定（"等你处理的工单"）。

**F-27｜低｜对话里每条消息的链接和事务本身的链接用了同一句文案**

- **位置**：`src/client/conversation.tsx:20`（每条消息跳到对应评论）和 `:69`（跳到事务）都用 `t('pmsOpenInRedmine')` = "在 Redmine 中查看"

- **为什么伤害**：轻微伤害问题三（追溯这段工作的历史）——回溯锚点是操作员回到真相源的唯一路径。
- **建议**：消息级链接改成带编号或时间的标签（"在 Redmine 中查看第 3 条"）。

### 2.7 可访问性

---

**F-33｜中｜流水线图例对读屏用户不存在**

- **位置**：`src/client/dashboard.tsx:81` — `<span className="dt-pipe-legend" aria-hidden="true">`

- **为什么伤害**：读屏用户能读到站名和数字，但读不到"绿色代表进行中、琥珀色代表等人"这条映射，于是颜色对TA完全不存在。

**F-34｜中｜流水线站点按钮的可访问名里没有"点它会去哪里"**

- **位置**：`src/client/pipeline.tsx:57` — `<button className="dt-station dt-station-open" onClick={station.onOpen}>{body}</button>`，`body` = 光点 + 站名 + 数字 + 说明（`pipeline.tsx:31-42`）

- **为什么伤害**：伤害问题二（读屏用户少了一条导航线索），也让这 7 个按钮在辅助技术眼里像 7 个无名按钮。
- **建议**：给按钮加 `aria-label`（"任务 4 个，其中 2 个已接单 — 打开收件箱"），或加一个视觉隐藏的说明。

**F-35｜中｜横幅状态变化从不播报**

- **位置**：`src/client/dashboard.tsx:32` — `<div className="dt-live" data-state={state}>`，不是 live region；内容每 5 秒被轮询替换
- **发生什么**：系统从"运行中"变成"已暂停"、任务系统变成"没有响应"，读屏用户不会收到任何通知——横幅不是 `aria-live` 区域。
- **为什么伤害**：伤害问题二。恰恰是最需要被立刻知道的变化（系统挂了）没有任何播报。
- **建议**：给横幅加 `role="status"`（或 `aria-live="polite"`），并且只在状态值变化时更新内容，避免每次轮询都刷屏。

### 2.8 空状态与错误状态

---

**F-36｜高｜任务系统连不上时，工作台给出的空状态是一句假话**

- **位置**：`src/client/pms.tsx:58` — `{data.source.error && <p className="dt-error dt-mono dt-clamp">{data.source.error}</p>}`；服务端 `src/app/views/pms.ts:144-146` 捕获失败后返回 `issues: [], connected: false, error`；列表空态 `src/client/pms.tsx:40` → `t('pmsNoTasks')` = "没有指派给你的任务。/ No task is assigned to you."
- **发生什么**：任务系统不可达时，操作员看到的是：上面一行等宽的原始错误，然后三个计数为 0 的筛选胶囊，然后一句 **"没有指派给你的任务"**。这句话是假的——任务存在，只是面板读不到。
- **为什么伤害**：直接伤害问题一，违反原则 5（诚实状态）。一句错误的空状态比一个错误提示更有害：操作员会认为今天没有活，转而去别处确认。
- **建议**：把"任务系统未连接"做成明确的空态（说明读不到、给出重试、显示最后一次成功读取的时间），不要落到"没有任务"这句上。

---

**F-37｜中｜轮询失败时，错误以 `role="alert"` 的形式出现在一个完全正常的列表上方**

- **位置**：`src/client/pms.tsx:56` — `<LoadState error={error} loading={!data} />`；`src/client/widgets.tsx:113-117` — 有 error 就渲染 `<p className="dt-error" role="alert">{error.message}</p>`
- **发生什么**：一次瞬时轮询失败就会在好端端的列表上方插一条红色 alert 行，而列表本身照常显示（旧数据）。每 5 秒一次失败就是每 5 秒一条红色行。
- **为什么伤害**：伤害问题二，也让读屏用户被反复打断；更糟的是红色 alert 出现在一个其实可用的列表上方，暗示"页面坏了"。
- **建议**：有旧数据时把错误降级成一行不显眼的提示（"数据可能不是最新的"），只有完全没数据时才用 `role="alert"`。

---

**F-38｜中｜什么都在正常运行时，概览仍然渲染一整张 7 个 0 的图**

- **位置**：`src/client/overview.tsx:68` 无条件渲染 `LiveDashboard`；`src/client/pipeline.tsx:26-29` 的比例对全 0 也照常算（`Math.max(1, ...)`）
- **发生什么**：系统健康、零任务时，页面最显眼的一块是七个写着 0 的站点，每个站点带光点、说明行、进度条——整页最费空间的一块承载了零信息。
- **为什么伤害**：违反原则 6（健康状态不占额外空间）。它把"没事"画成了"有事的样子"，操作员每次都要再确认一遍那些 0。
- **建议**：全部计数为 0 时把图收成一行安静文字（"流水线：没有进行中的工作"），有内容再展开成图。

---

**F-39｜低｜概览的加载态是一行 13px 的暗色提示，没有骨架**

- **位置**：`src/client/overview.tsx:65` — `if (!data) return <LoadState error={error} loading />` → `src/client/widgets.tsx:116` — `loading ? <Hint>{t('loading')}</Hint> : null`；`.dt-hint` 是 13px 三级色（`client.css:23`）
- **发生什么**：首屏加载时整个页面只剩一行灰字，随后整块内容突然出现。
- **为什么伤害**：轻微伤害问题一——首屏没有稳定的形状，操作员要等页面重排。
- **建议**：至少给横幅和流水线卡片一个固定高度的骨架，避免布局跳动。

---

**F-40｜低｜`canReply` 永远是 true，"现在不能回复"那段文案是死代码**

- **位置**：服务端 `src/app/views/pms.ts:278` — `canReply: true` 硬编码；客户端 `src/client/conversation.tsx:91` — `{data.canReply ? <form …> : <p className="dt-hint">{t('pmsNoReply')}</p>}`
- **发生什么**：任务系统未配置时 `pmsTask` 直接返回 undefined、接口 404（`pms.ts:266`），根本走不到 `canReply: false` 分支；那段"这个任务现在不能回复"的文案从未被验证过。
- **为什么伤害**：低。它是一段没有对应真实状态的文案，重设计时容易把不存在的分支当契约。
- **建议**：要么真正按连接状态返回 `canReply`，要么删掉这条分支和它的文案。

## 3. 做得好的地方

重设计时不要丢掉的：

1. **流水线图是导航面，不是插画** — 七个站点每一个都指向"装着这类工作的那个页面"（`dashboard.tsx:56-71` 逐个给 `onOpen`）。图和操作路径是一体的。
2. **同一个状态函数驱动横幅、动画和站点色调** — `liveState()`（`dashboard.tsx:19-21`）一个函数同时决定横幅颜色（`:32`）、流水线是否流动（`:88` `flowing={liveState(data) === 'running'}`）和七个站点的 tone（`:54`）。没有一个地方能显示互相矛盾的状态。
3. **信标是装饰，状态词是正文** — `.dt-live-beacon` 标了 `aria-hidden`（`dashboard.tsx:33`），"运行中 / 已暂停 / 没有响应"是真实文本（`:35`）。状态不依赖颜色也能读。
4. **默认安静做到了位** — 概览在没有问题时**整段不渲染**问题区块（`overview.tsx:75` `data.problems.length > 0 && …`）；没有待处理工单时只有一句提示（`:73`）。健康时不占地方。
5. **需要人处理的行把动作直接放在行里** — `TicketLine` 在行内渲染"在来源里回答 / 重试 / 停止 / 打开 Session"（`rows.tsx:31-41`），操作员不必先进工单详情才能回答。
6. **破坏性操作确认，而且确认文案写清了影响范围** — 删除的确认语是"只从工作台隐藏，不删除 Redmine 事务；正在处理它的工单会继续"（`pms.tsx:30` → `pmsDeleteMessage`），正好是操作员在点之前需要知道的那一句。
7. **计数徽标和它下面的列表是同一个数** — `Section` 的 `count` 与 children 里的列表同源（`widgets.tsx:30` + `overview.tsx:70-72`），原则 5 在区块这一层是被遵守的。
8. **整行可点，但行内控件不被吞掉** — `.dt-open::after` 把整行变成标题按钮的点击区（`client.css:102`），同时 `.dt-ticket-actions, .dt-row-buttons, .dt-row-actions { pointer-events: none }` 且子元素恢复 `pointer-events: auto`（`client.css:399-400`）。大点击区 + 不误触。
9. **键盘可达性做得扎实** — 标签栏方向键切换后把焦点移到新选中的标签（`controls.tsx:72-82` `walk()`）；弹窗有焦点陷阱、Esc 关闭、关闭后焦点还给触发元素（`controls.tsx:191-201`）；`prefers-reduced-motion` 下信标、灯条、流动动画全部停止（`client.css:91-95`）。
10. **悬停才出现的行操作，键盘聚焦时也会出现** — `.dt-task-actions` 默认 `opacity: 0`，但 `:hover / [data-selected] / :focus-within` 时显示（`client.css:468-469`）。行面干净，键盘用户也没被关在门外。
11. **轮询钩子保留上一次的好数据、丢弃过期响应** — `usePoll`（`api.ts:67-98`）在瞬时失败时不清空页面，切换路由时旧响应不会覆盖新数据。
12. **状态是算出来的，不是存出来的** — `taskOf()` 用工单阶段 + 线程最后一次决策推导出任务状态（`src/app/views/pms.ts:174-176`），所以"待分析 / 未处理 / 分析中 / 等你处理 / 已完成"这五个标签都有可判定的定义（原则 2）。
13. **Agent 的笔记带标记，面板读的时候把标记剥掉** — `withoutMarkers()`（`pms.ts:110`）+ 角色判定（`:252`），对话因此读起来是对话而不是日志。
