# 011 交互场景清单

这份清单是模拟时逐条走查用的：每一行写清楚**谁做什么、系统应该怎么反应**。
标着「待定」的行还没有定下期望的行为，模拟的时候一起商量；其余的行模拟时把
结果记在最后一列。

角色只有三个：**团队负责人**（Redmine 里叫这个，Gerrit 里是 `lead`）派任务，
**开发工程师**（`dev`）是干活的人，**超级智能体**是开发工程师的助手——它没有
自己的账号，借用开发工程师的账号在任务系统和代码评审服务器上说话。

环境是中文的：任务系统里的工单是中文的，代理在工单里和评审里的回复也是中文的。

## 1. 一个任务在工作台上的状态

代理接到的每一个工单（指派给 `dev` 的），都落在下面某个状态里。状态是工作台
上看得见的：任务列表里每一条都带着它的状态。

| 状态 | 含义 | 谁让它进入这个状态 | 工作台上的样子 |
|------|------|------------------|--------------|
| 待分析 | 代理还没有判断要不要接 | 任务指派给 `dev` | 在「待处理」里，标 *待分析* |
| 未处理 | 判断结果是不该接 | route 分析 | 在「未处理」里，写明原因 |
| 分析中 | 接了单，正在读代码、动手 | route 分析判断该接 | 在「待处理」里，标 *分析中* |
| 等待你 | 需要人做事：回答一个问题、给个许可、验收 | 代理 | 在「待处理」里，标 *等你处理*，把问题写出来 |
| 已完成 | 活干完了，补丁在评审服务器上等人评审 | 代理 | 在「待处理」里，标 *已完成*，带变更单链接 |
| 已归档 | 人验收过了，收起来 | 开发工程师点归档 | 在「已归档」里 |

状态之间只往前的路径：

```
待分析 ──不该接──> 未处理
   │
   └──该接──> 分析中 ──问人──> 等待你 ──人回答──> 分析中
                  │
                  ├──干完──> 已完成 ──人验收归档──> 已归档
                  └──干不下去──> 等待你（阻塞）
```

## 2. 接单判断（route 分析）

代理拿到指派给 `dev` 的工单，先判断该不该接。这一步只读任务系统里的内容，不动代码。

| # | 场景 | 期望的行为 | 状态 |
|---|------|------------|------|
| 2.1 | 工单是开发工程师自己的，指派给他，发送者是名单上的团队负责人 | 接单，进入分析 | 已模拟 |
| 2.2 | 工单指派给 `dev`，但发送者不在这个来源的名单里 | 不接单，归档为「未处理」，写明「发送者不在这个来源的名单里」 | 已模拟 |
| 2.3 | 工单指派给 `dev`，但任务系统的准入规则把这种请求排除了 | 不接单，归档为「未处理」，写明被哪条规则排除 | 待模拟 |
| 2.4 | 工单指派给 `dev`，但内容里没有提到代理，也没有理由主动做 | 不接单，归档为「未处理」（没有人提这件事） | 待模拟 |
| 2.5 | 工单指派给 `dev`，内容像是一个可以顺手做的小修（符合某条已启用的规则） | 按规则接单 | 待模拟 |
| 2.6 | 工单指派给 `dev`，但团队负责人明确说「这件事不用代理做」 | 不接单 | 待模拟 |
| 2.7 | 工单指派给 `dev`，但同时指派了别人（任务不是他的） | 不接单 | 待模拟 |
| 2.8 | 同一个工单被重复触发（轮询、重复评论） | 不重复接单、不重复干活 | 待模拟 |
| 2.9 | 接单判断时模型或服务不可用 | 不当成「不该接」，工单留在「待分析」，面板上显示错误 | 待模拟 |

## 3. 接单之后：分析

| # | 场景 | 期望的行为 | 状态 |
|---|------|------------|------|
| 3.1 | 工单描述完整：有症状、有复现步骤、有期望行为、指名了文件 | 直接动手：克隆工单指名的仓库，改代码，跑测试，推变更单 | 已模拟 |
| 3.2 | 工单只有一句话，没有复现步骤，也没有指名文件 | 回到工单里问一次：问具体的问题（缺什么、期望什么），不猜着做 | 已模拟 |
| 3.3 | 工单指名了文件，但仓库里找不到这个文件 | 报告阻塞：说清缺什么，需要人做什么 | 待模拟 |
| 3.4 | 工单指名的项目在代码评审服务器上没有对应的仓库 | 报告阻塞，不去改别的仓库 | 待模拟 |
| 3.5 | 需求有多种实现方式，代价差别大 | 问一次，给出选项和代价 | 待模拟 |
| 3.6 | 同一个缺陷已经有人修了（评审服务器上已有变更单） | 认出已有的变更，不重复改 | 已模拟 |
| 3.7 | 分析到一半发现工单里的信息互相矛盾 | 问人，把矛盾指出来 | 待模拟 |
| 3.8 | 分析中发现要改的地方超出工单说的范围 | 只做工单授权的范围，其余写进报告 | 待模拟 |

## 4. 处理完：交付与验收

| # | 场景 | 触发者 | 期望的行为 | 状态 |
|---|------|--------|------------|------|
| 4.1 | 补丁推上评审服务器，等人评审 | — | 工单上是「已完成」，带变更单链接；不催、不重复汇报 | 已模拟 |
| 4.2 | 团队负责人在变更单上留评审意见（改法不对） | 团队负责人 | 在同一个工单上改，推一个新的 patch set，在变更单上回一句 | 待模拟 |
| 4.3 | 团队负责人 +2 并合并 | 团队负责人 | 工单结束（已完成），代理在工单里回报结果和链接 | 已模拟 |
| 4.4 | 团队负责人直接放弃了变更单 | 团队负责人 | 代理看到变更已放弃，停手，在工单里说明 | 待模拟 |
| 4.5 | 开发工程师验收之后点归档 | 开发工程师 | 任务从「待处理」移到「已归档」，任务系统里的工单不动 | 已模拟 |
| 4.6 | 团队负责人在工单里追加一条要求 | 团队负责人 | 接着同一个工单继续做，不新开一单 | 已模拟 |
| 4.7 | 团队负责人明确说「先别做了」 | 团队负责人 | 停止这个工单，状态回到「等待你」或结束 | 待模拟 |
| 4.8 | 代理写的代码测试不过 | — | 自己先修；真修不好才来问人 | 待模拟 |
| 4.9 | 代理没有权限（不能提交、不能合并） | — | 报告阻塞，说清需要人做的最小动作 | 待模拟 |

## 5. 回复的把控

代理在工单里和评审上的每一句话，都受三样东西约束：

1. **沟通策略**（面板 → 设置 → 提示词 → *Communication*，团队可改）：什么时候说、
   说什么、说多长、什么形状。里面带着模板：
   - 确认（ acknowledgement ）：「收到，我在改 X。」
   - 交付（ completion ）：「修复已提交：<变更单链接>，可以审阅了。」
   - 阻塞（ blocker ）：「机器人读不到这份文档，所以没法确认需求，请给机器人开通读取权限。」
   - 每条工单笔记和每条评审消息都以此开头：「本条内容由自动代理发出，并非真人。」
   - 默认是**干活时保持安静**：只有成品、真正的阻塞、或者人直接问，才说话。
2. **授权与名单**：谁能跟代理说话（这个来源的名单）、什么时候可以主动做事（规则）。
3. **代码评审服务器上的规矩**：作者不能合并自己的变更单，所以合并永远是人的事。

语言跟对话走：对话是中文，回复就是中文。

| # | 动作 | 期望的行为 | 状态 |
|---|------|------------|------|
| 6.1 | 在「未处理」里看一眼某条为什么不接 | 看到原因（不在名单／被规则排除／没人提） | 待模拟 |
| 6.2 | 归档一个任务 | 从「待处理」移到「已归档」，任务系统里的工单不动 | 已模拟 |
| 6.3 | 从「已归档」里放回来 | 回到「待处理」 | 待模拟 |

| 6.6 | 停止一个执行中的工单 | 停下来 | 待模拟 |

## 7. 第一轮走查的结果（2026-11-08）

| 场景 | 结果 | 说明 |
|------|------|------|
| 2.1 该接单 | 通过 | 领导建的工单，代理接了，状态从「待分析」变成「分析中」 |
| 2.2 不该接单 | 通过 | 系统管理员建的工单进了「未处理」，写明"发送者不在这个来源的名单里" |
| 3.1 信息完整 | 通过 | 代理直接动手，改完推了变更单 8，用中文在工单上回报，链接可点 |
| 3.6 别人已经修过 | 未走到 | 这轮没有准备重复缺陷的场景 |
| 4.1 等人评审 | 通过 | 代理推完就停，工单上不催、不重复汇报 |
| 4.3 合并后收尾 | **有问题** | 合并之后"已合入"的通知没有自己送到工单上 |
| 4.5 验收归档 | 通过 | 开发工程师在工作台归档，工单进了「已归档」，任务系统里的工单不动 |
| 4.6 追加要求 | 通过 | 领导在工单里追加要求，代理接着同一个工单做，推了新的 patch set 2，没有新开单 |
| 评审意见 | 通过 | 代理先核对，发现用例已经在 patch set 3 里，就只回了一句事实说明，没有多推补丁 |

**发现的三个问题**

1. **信息不足时不会来问。** 工单只说"用起来很慢"，代理自己定了方向就动手了，还顺手把
   "答案用压缩传输"这种工单没要求的改动做了。`prompts/work.md` 里"Choose reasonable
   defaults instead of asking the human to manage routine steps"压过了"目标不明确时问一次"
   的要求，后者只写在主动触发的那一段里。
2. **合并之后通知没有自己送到工单上。** 合并的消息送达 worker 的那一刻，正好是 worker
   这一轮结束的时刻：消息标记为已送达，worker 却没有开始下一轮，工单停在"等你处理"，
   assignment 一直显示"运行中"。两次合并都是这样；只有人再对工单说一句话，代理才会
   发现变更已经合入，工单才会结束。
3. **代理自己的标记漏到了 Gerrit 界面上。** 工单笔记里的标记会被面板去掉，Gerrit 的
   评审消息里的 `<!-- dsh-superagent:… -->` 会显示出来。

## 8. 模拟的时候记什么

- 工单号、变更单号；
- 代理在工单里和变更单上的原话（中文）；
- 代理做了什么、没做什么；
- 和期望不一致的地方，以及该由规则、提示词还是人来定。

跑完一轮之后，把这一行挪到「已模拟」，把结论写进 `docs/004-prompts.md`
（提示词要改的地方）和 `docs/002-authorization.md`（名单和准入要改的地方）。
